# Secret Management

This document is the authoritative reference for how secrets are generated, wired, rotated, and
audited in the `ssl-proxy` stack. It complements the operational procedures in `docs/runbook.md`.

---

## 1. Canonical Secrets Layout

All secrets live at the repository root under `secrets/`. This directory is **git-ignored** and
created only at deployment time by `scripts/gen-secrets.pl`.

```
secrets/
├── postgres.key                         # POSTGRES_PASSWORD
├── minio_access_key.key                  # MINIO_ACCESS_KEY_ID
├── minio_secret_key.key                  # MINIO_SECRET_ACCESS_KEY
├── admin_api_key                         # ssl-proxy ADMIN_API_KEY (no .key suffix)
├── wg_obfuscation_key                    # WG obfuscation key
├── grafana_admin_password.key            # GF_SECURITY_ADMIN_PASSWORD
├── atheros_api_token_sha256.key          # ATHSEARCH_API_TOKEN_SHA256 (hex hash)
├── wg-rotation/
│   ├── frontdoor/
│   │   └── wg-udp-frontdoor.toml        # frontdoor config (not generated by gen-secrets.pl)
│   └── candidate/
│       └── secrets/
│           ├── admin_api_key             # copy of admin_api_key for rotation candidate
│           └── wg_obfuscation_key        # copy of wg_obfuscation_key for rotation candidate
└── waha/
    ├── api_key.key                       # WAHA_API_KEY
    ├── dashboard_password.key            # WAHA_DASHBOARD_PASSWORD
    └── swagger_password.key              # WHATSAPP_SWAGGER_PASSWORD
```

File permissions: `0600` for all secret files, `0700` for all directories in the tree.

## 2. Secret Generation

### 2.1 One-time bootstrap

Run the generation script **once per environment** on the target server:

```bash
perl scripts/gen-secrets.pl
```

The script:

| Step | Detail |
|---|---|
| Entropy source | Reads from `/dev/urandom` via `sysopen`/`sysread` |
| Encoding | `MIME::Base64` (core Perl module, no CPAN) with padding stripped |
| Atomic writes | Writes to `path.tmp.PID` then `rename(2)` to final path |
| Permissions | Files `0600`, directories `0700`, applied via `Fcntl` constants |
| Hash storage | Atheros token stores SHA-256 hex digest; raw token printed to stderr once |

### 2.2 What gets generated

| File | Bytes of entropy | Encoded length | Used by |
|---|---|---|---|
| `postgres.key` | 32 | ~43 chars | Postgres, postgres-exporter |
| `minio_access_key.key` | 24 | ~32 chars | MinIO, java-coordinator, integration-console web, minio-init |
| `minio_secret_key.key` | 32 | ~43 chars | Same as above |
| `wg_obfuscation_key` | 32 | ~43 chars | ssl-proxy, wg-obfs-shim clients |
| `admin_api_key` | 48 | ~64 chars | ssl-proxy admin API |
| `grafana_admin_password.key` | 32 | ~43 chars | Grafana |
| `atheros_api_token_sha256.key` | 48 | hex(64) | atheros-search |
| `waha/api_key.key` | 32 | ~43 chars | Waha WhatsApp bridge |
| `waha/dashboard_password.key` | 32 | ~43 chars | Waha dashboard |
| `waha/swagger_password.key` | 32 | ~43 chars | Waha Swagger UI |

The script also copies `admin_api_key` and `wg_obfuscation_key` into
`wg-rotation/candidate/secrets/` so the `ssl-proxy-next` rotation candidate picks them up.

### 2.3 Important notes

- **Never run the script twice in the same environment** unless you intend to rotate *all* secrets.
  Existing files will be overwritten.
- The raw Atheros API token is printed to stderr **once** at generation time and is not stored
  anywhere. Save it immediately:
  ```
  perl scripts/gen-secrets.pl 2>&1 | tee gen-output.txt
  ```
- The script does not create the `wg-rotation/frontdoor/wg-udp-frontdoor.toml` file. That is
  maintained by the WireGuard key rotator (`apps/wg-key-rotator/bin/wg_key_rotator`).

## 3. Runtime Wiring

### 3.1 The `.env` file

Create `.env` at the repository root (also git-ignored) using `.env.example` as a template:

```bash
cp .env.example .env
# Then edit .env to point to your generated secrets
```

The `.env` file is automatically loaded by `docker compose`. It reads secret files and exports the
variables consumed by the compose file.

### 3.2 Direct env var vs `_FILE` variant

Some services support a `_FILE` variant that reads the secret from a mounted file path instead of
an environment variable. The compose file uses `_FILE` for services that support it and direct env
vars for everything else.

| Pattern | Services | Example |
|---|---|---|
| Direct `${VAR?}` | Postgres, MinIO, Grafana, postgres-exporter | `POSTGRES_PASSWORD=${POSTGRES_PASSWORD?}` |
| Direct `${VAR:-fallback}` | Integration console DB URLs, Atheros search | `ATHSEARCH_API_TOKEN_SHA256=${ATHSEARCH_API_TOKEN_SHA256:-}` |
| `_FILE` variant | ssl-proxy, ssl-proxy-next, java-coordinator | `ADMIN_API_KEY_FILE=/run/local-secrets/admin_api_key` |

The `?` suffix causes Docker Compose to fail immediately if the variable is unset. This is used
for secrets that must always be present (Postgres, MinIO, Grafana). Variables with `:-` fall back
to an empty string or a reasonable default for development.

### 3.3 Volume mounts for file-based secrets

```
ssl-proxy:          ./secrets:/run/local-secrets:ro
ssl-proxy-next:     ./secrets/wg-rotation/candidate:/run/wg-rotation/candidate:ro
java-coordinator:   ./secrets:/run/secrets:ro
```

## 5. Rotation Procedures

### 5.1 Postgres password (planning required)

Postgres credentials are consumed by multiple services. Rotation requires a coordinated restart:

1. Update the secret file: `openssl rand -base64 32 | tr -d '\n' > secrets/postgres.key`
2. Update `.env` (if you source it) or just restart services so they re-read the file
3. Restart postgres: `docker compose up -d postgres` (this restarts with the new password)
4. Restart every service that connects to postgres: `docker compose up -d java-coordinator integration-console-web integration-console-worker integration-console-db-setup integration-console-heatmap-refresh integration-console-heartbeat postgres-exporter atheros-sensor`
5. Verify: `docker compose logs postgres | grep "password"` (should show no auth failures)

**After a Postgres password change**, old `DATABASE_URL` values with embedded `sync:sync@` in
defaults will still work because they are only fallbacks — the actual password comes from
`${POSTGRES_PASSWORD?}` which reads from `.env`. If you source `.env` via `($ cat secrets/postgres.key)`, no URL edit is needed.

### 5.2 MinIO credentials (planning required)

1. Update both secret files: regenerate `minio_access_key.key` and `minio_secret_key.key`
2. Restart minio: `docker compose up -d minio`
3. Restart minio-init: `docker compose up -d minio-init` (recreates buckets with new creds)
4. Restart consumers: `docker compose up -d java-coordinator integration-console-web`
5. Verify: `docker compose logs minio-init | grep "bucket_ready"` should show success

### 5.3 WireGuard obfuscation key

The obfuscation key is file-based and read at startup. To rotate without restarting the main proxy,
use the key rotator workflow in `docs/runbook.md` section 3, which spins up the `ssl-proxy-next`
candidate and migrates peers.

For a simple key rotation (accepts brief window of mismatched keys):

1. Update `secrets/wg_obfuscation_key`
2. Update `secrets/wg-rotation/candidate/secrets/wg_obfuscation_key`
3. Restart `ssl-proxy`: `docker compose restart ssl-proxy`
4. Restart `wg-udp-frontdoor`: `docker compose restart wg-udp-frontdoor`
5. Distribute new key to client `wg-obfs-shim` instances

### 5.4 Admin API key

The admin API key is file-based via `ADMIN_API_KEY_FILE`. Rotation is a simple file write and
process reload:

1. Generate new key: `openssl rand -base64 48 | tr -d '\n' > secrets/admin_api_key`
2. Copy to rotation candidate: `cp secrets/admin_api_key secrets/wg-rotation/candidate/secrets/admin_api_key`
3. Restart `ssl-proxy`: `docker compose restart ssl-proxy`
4. If `ssl-proxy-next` is running: `docker compose --profile rotation restart ssl-proxy-next`
5. Verify: `curl -H "X-API-Key: $(cat secrets/admin_api_key)" http://127.0.0.1:3002/health`

### 5.5 Atheros API token

The token is SHA-256 hashed, so clients must be updated with the raw token:

1. Generate new raw token and hash:
   ```bash
   RAW_TOKEN=$(openssl rand -base64 48 | tr -d '\n')
   echo -n "$RAW_TOKEN" | sha256sum | awk '{print $1}' > secrets/atheros_api_token_sha256.key
   ```
2. Update `.env` or `.env` sources the file — restart `atheros-search`:
   `docker compose --profile vector up -d atheros-search`
3. Distribute the new raw token to all API clients
4. Verify: clients with old token receive `401`; clients with new token receive `200`

### 5.6 Waha credentials

1. Regenerate the needed key file(s) in `secrets/waha/`
2. Update `.env` (if you source it directly) or restart the waha service
3. Restart: `docker compose --profile rotator up -d waha`
4. Verify via the Waha dashboard or API health endpoint

## 6. Incident Response

### 6.1 Secret committed to git

1. **Do not** delete the commit and force-push if others may have pulled it.
2. Rotate the compromised secret immediately using the procedure in section 5.
3. Remove the file from history with `git filter-branch` or `git filter-repo` only after the
   secret is rotated and all services updated.
4. If the secret appeared in a public repo or a log aggregator, treat it as fully compromised.

### 6.2 Secret leaked via logs

1. If a secret value appeared in `docker compose logs`, identify which service logged it.
2. Rotate that secret using section 5.
3. Investigate the logging configuration: add redaction rules or fix the log statement.
4. Check external log aggregators (Loki, Promtail, etc.) for cached copies and purge them.

### 6.3 Emergency full rotation

```bash
# 1. Generate all new secrets
perl scripts/gen-secrets.pl

# 2. Update .env
source .env.example > .env    # update with new values

# 3. Recreate everything
docker compose down --remove-orphans
docker compose up -d --build

# 4. Distribute new client keys (WireGuard PSK, obfuscation key, Atheros token)
```

## 7. Verification Commands

After any secret change, run these to confirm correct wiring:

```bash
# 1. Check no hardcoded credentials remain in compose configuration
docker compose config | grep -E 'senhamaster123|administrador' && echo "🔴 LEAK DETECTED" || echo "✅ No legacy creds"

# 2. Verify all `${VAR?}` references are resolved (will error if any are missing)
docker compose config > /dev/null 2>&1 && echo "✅ Compose config valid" || echo "🔴 Missing vars"

# 3. Check postgres auth
docker compose exec -T postgres psql -U sync -d sync -c "SELECT 1" && echo "✅ Postgres auth OK" || echo "🔴 Postgres auth failed"

# 4. Check MinIO auth
curl -s http://127.0.0.1:9000/minio/health/live > /dev/null && echo "✅ MinIO reachable" || echo "🔴 MinIO unreachable"

# 5. Check Grafana auth (requires token or cookie, but login page indicates reachable)
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3004/login

# 6. Check ssl-proxy admin API
curl -s -H "X-API-Key: $(cat secrets/admin_api_key)" http://127.0.0.1:3002/health | grep -q '"status":"ok"' && echo "✅ Admin API OK" || echo "🔴 Admin API failed"

# 7. Confirm secret file permissions
find secrets -type f ! -perm 600 -ls 2>/dev/null && echo "🔴 Wrong file permissions" || echo "✅ File permissions correct"
find secrets -type d ! -perm 700 -ls 2>/dev/null && echo "🔴 Wrong dir permissions" || echo "✅ Dir permissions correct"
```

## 8. Developer Rules

**Do not:**
- Generate secrets. Run `perl scripts/gen-secrets.pl` only on the target server.
- Copy `secrets/` to your laptop or another machine.
- Paste a secret value into Slack, a ticket, or a PR description.
- Commit `.env`, `secrets/`, any `*.key`, `*.pem`, or `*.secret` file.
- Add a secret as a default value in compose (e.g. `${MY_SECRET:-actual_value_here}`).
  Empty string defaults only.
- Log a secret value. Log *that* it was loaded.
- Pass a secret as a CLI argument (visible in `ps aux`).

**Do:**
- Use `_FILE` env vars where the service supports them (`ADMIN_API_KEY_FILE`,
  `ORACLE_PASS_FILE`, `WG_OBFUSCATION_KEY_FILE`).
- If you need a new secret, open a ticket. Do not invent your own env var and compose key
  without review.
- For local dev, run the generation script locally into a local `secrets/` that stays on your
  machine. Never use production secrets locally.
