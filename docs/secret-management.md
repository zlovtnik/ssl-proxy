# Secret Management

This document is the authoritative reference for how secrets are generated, wired, rotated, and
audited in the `ssl-proxy` stack. It complements the operational procedures in `docs/runbook.md`.

---

## 1. Canonical Secrets Layout

All secrets live at the repository root under `secrets/`. This directory is **git-ignored** and
created only at deployment time by `scripts/gen-secrets`.

```
secrets/
├── postgres.key                         # POSTGRES_PASSWORD
├── minio_access_key.key                  # MINIO_ACCESS_KEY_ID
├── minio_secret_key.key                  # MINIO_SECRET_ACCESS_KEY
├── admin_api_key                         # ssl-proxy ADMIN_API_KEY (no .key suffix)
├── wg_obfuscation_key                    # WG obfuscation key
├── grafana_admin_password.key            # GF_SECURITY_ADMIN_PASSWORD
├── oracle_password.txt                   # ORACLE_PASS_FILE for java-coordinator
├── atheros_api_token_sha256.key          # ATHSEARCH_API_TOKEN_SHA256 (hex hash)
├── schema-migrator/
│   ├── encrypt_key.key                    # Base64 AES-256-GCM key
│   ├── jwt_secret.key                     # backend internal JWT signing secret
│   ├── api_bearer_token.key               # backend static API token
│   ├── state_db_password.key              # dedicated PostgreSQL state role password
│   ├── keycloak_database_password.key     # dedicated Postgres role password
│   ├── keycloak_bootstrap_admin_password.key # Keycloak master bootstrap password
│   └── application_admin_password.key     # schema-admin initial temporary password
├── ONE_TIME_TOKENS                       # raw bootstrap tokens to consume and delete
├── wg-rotation/
│   ├── frontdoor/
│   │   └── wg-udp-frontdoor.toml        # frontdoor config (not generated by secret bootstrap)
│   └── candidate/
│       └── secrets/
│           ├── admin_api_key             # copy of admin_api_key for rotation candidate
│           └── wg_obfuscation_key        # copy of wg_obfuscation_key for rotation candidate
└── waha/
    ├── api_key.key                       # WAHA_API_KEY
    ├── dashboard_password.key            # WAHA_DASHBOARD_PASSWORD
    └── swagger_password.key              # WHATSAPP_SWAGGER_PASSWORD
```

File permissions: `0400` for file-backed runtime keys (`admin_api_key`,
`wg_obfuscation_key`, and rotation candidate copies), `0444` for `oracle_password.txt`
because the non-root coordinator reads it through a read-only bind mount, `0600` for other
generated secret files, `0711` for the top-level `secrets/` directory, and `0700` for nested
secret directories. `ONE_TIME_TOKENS` is always `0600`.

## 2. Secret Generation

### 2.1 One-time bootstrap

Run the generation wrapper **once per environment** on the target server:

```bash
scripts/gen-secrets generate
SERVER_IP=<server-local-ip> scripts/gen-secrets env
```

The wrapper calls the Elixir rotator CLI (`wg_key_rotator secrets ...`):

| Step | Detail |
|---|---|
| Entropy source | Uses Erlang/OTP `:crypto.strong_rand_bytes/1` |
| Encoding | URL-safe base64 without padding for generated literal values; the Schema Migrator AES key uses standard Base64 so Java decodes exactly 32 bytes |
| Atomic writes | Writes a temporary file, applies mode, then renames to the final path |
| Overwrite policy | Refuses to overwrite managed files unless `--force` is passed |
| Permissions | Applies per-secret file modes and locks generated directories to `0700` |
| Repair | Fixes managed modes and rewrites candidate secret copies without replacing root secrets |
| Hash storage | Atheros token stores SHA-256 hex digest; raw token is written once to `secrets/ONE_TIME_TOKENS` |

### 2.2 What gets generated

| File | Bytes of entropy | Encoded length | Used by |
|---|---|---|---|
| `postgres.key` | 32 | ~43 chars | Postgres, postgres-exporter |
| `minio_access_key.key` | 24 | ~32 chars | MinIO, java-coordinator, minio-init |
| `minio_secret_key.key` | 32 | ~43 chars | Same as above |
| `wg_obfuscation_key` | 32 | ~43 chars | ssl-proxy, wg-obfs-shim clients |
| `admin_api_key` | 48 | ~64 chars | ssl-proxy admin API |
| `grafana_admin_password.key` | 32 | ~43 chars | Grafana |
| `oracle_password.txt` | 32 | ~43 chars | java-coordinator Oracle sink |
| `atheros_api_token_sha256.key` | 48 | hex(64) | atheros-search |
| `schema-migrator/encrypt_key.key` | 32 | 44 chars | Schema Migrator AES-256-GCM response and target-password encryption |
| `schema-migrator/jwt_secret.key` | 48 | ~64 chars | Schema Migrator internal JWT signing |
| `schema-migrator/api_bearer_token.key` | 48 | ~64 chars | Static backend API authentication |
| `schema-migrator/state_db_password.key` | 32 | ~43 chars | Schema Migrator PostgreSQL state role |
| `schema-migrator/keycloak_database_password.key` | 32 | ~43 chars | Keycloak's dedicated `keycloak` Postgres role |
| `schema-migrator/keycloak_bootstrap_admin_password.key` | 32 | ~43 chars | Keycloak master-realm bootstrap administrator |
| `schema-migrator/application_admin_password.key` | 24 | ~32 chars | Initial temporary password for `schema-admin` |
| `waha/api_key.key` | 32 | ~43 chars | Waha WhatsApp bridge |
| `waha/dashboard_password.key` | 32 | ~43 chars | Waha dashboard |
| `waha/swagger_password.key` | 32 | ~43 chars | Waha Swagger UI |

The generator also copies `admin_api_key` and `wg_obfuscation_key` into
`wg-rotation/candidate/secrets/` so the `ssl-proxy-next` rotation candidate picks them up.

### 2.3 Important notes

- **Never run generation with `--force` in the same environment** unless you intend to rotate
  *all* managed secrets. Without `--force`, existing managed files are not overwritten.
- The raw Atheros API token and initial `schema-admin` password are written to
  `secrets/ONE_TIME_TOKENS` **once** at generation time. When `repair` adds the
  Schema Migrator secrets to an existing installation, it recreates this
  one-time file for the new administrator password.
  Save it outside the repository, then delete the file:
  ```
  cat secrets/ONE_TIME_TOKENS
  rm secrets/ONE_TIME_TOKENS
  ```
- `scripts/gen-secrets check` fails while `secrets/ONE_TIME_TOKENS` exists.
- `scripts/gen-secrets repair` fixes managed permissions, rewrites candidate copies from
  the active root secrets (or the pending generation), and syncs an existing
  `config/server/publickey-server` into generated `config/<peer>/*.conf` profiles.
- `oracle_password.txt` is generated so the coordinator mount contract is complete. For a real
  Oracle ADB sink, replace it with the actual `ORACLE_USER` password before enabling loads.
- `scripts/up-ready.sh` writes a local `secrets/up-ready-credentials.txt` handoff file on
  success. It is mode `0600` and contains the two peer configs, Postgres password, Grafana
  password, admin API key, WireGuard shim pass, magic byte, and Schema Migrator first-login
  credentials.
- The wrapper does not create the `wg-rotation/frontdoor/wg-udp-frontdoor.toml` file. That is
  maintained by the WireGuard key rotator (`apps/wg-key-rotator/bin/wg_key_rotator`).

## 3. Runtime Wiring

### 3.1 The `.env` file

Create `.env` at the repository root (also git-ignored) from the generated secret files:

```bash
SERVER_IP=<server-local-ip> scripts/gen-secrets env
```

The `.env` file is automatically loaded by `docker compose`. It contains literal values copied
from `secrets/`; it does not contain shell substitutions such as `$(cat ...)`. Set either
`REGISTRY=<registry-host>:5000` or `SERVER_IP=<server-local-ip>` when materializing `.env`; the
generator refuses to write an unresolved registry placeholder.

### 3.2 Direct env var vs `_FILE` variant

Some services support a `_FILE` variant that reads the secret from a mounted file path instead of
an environment variable. The compose file uses `_FILE` for services that support it and direct env
vars for everything else.

| Pattern | Services | Example |
|---|---|---|
| Direct `${VAR?}` | Postgres, MinIO, Grafana, postgres-exporter | `POSTGRES_PASSWORD=${POSTGRES_PASSWORD?}` |
| Direct `${VAR:-fallback}` | Integration console DB URLs | `DATABASE_URL=${DATABASE_URL:-postgres://sync:${POSTGRES_PASSWORD:?}@postgres:5432/sync}` |
| `_FILE` variant | ssl-proxy, ssl-proxy-next, java-coordinator | `ADMIN_API_KEY_FILE=/run/local-secrets/admin_api_key` |

The `?` suffix causes Docker Compose to fail immediately if the variable is unset. This is used
for secrets that must always be present (Postgres, MinIO, Grafana, WAHA credentials). Non-secret
variables may still use explicit development defaults.

### 3.3 Volume mounts for file-based secrets

```
ssl-proxy:          ./secrets:/run/local-secrets:ro
ssl-proxy-next:     ./secrets/wg-rotation/candidate:/run/wg-rotation/candidate:ro
java-coordinator:   ./secrets:/run/secrets:ro
```

| Compose Service | Secret | Env Variable(s) |
|---|---|---|
| `postgres` | `postgres.key` | `POSTGRES_PASSWORD` |
| `minio` | `minio_access_key.key`, `minio_secret_key.key` | `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` |
| `minio-init` | Same as minio | `MINIO_ACCESS_KEY_ID`, `MINIO_SECRET_ACCESS_KEY` |
| `java-coordinator` | Same as minio; `oracle_password.txt` | `MINIO_ACCESS_KEY_ID`, `MINIO_SECRET_ACCESS_KEY`; `ORACLE_PASS_FILE` |
| `grafana` | `grafana_admin_password.key` | `GF_SECURITY_ADMIN_PASSWORD` |
| `postgres-exporter` | `postgres.key` | `DATA_SOURCE_NAME` (embeds `POSTGRES_PASSWORD`) |
| `ssl-proxy` | `admin_api_key`, `wg_obfuscation_key` | `ADMIN_API_KEY_FILE`, `WG_OBFUSCATION_KEY_FILE` |
| `ssl-proxy-next` | rotation candidate copies | `ADMIN_API_KEY_FILE`, `WG_OBFUSCATION_KEY_FILE` |
| `atheros-search` | `atheros_api_token_sha256.key` | `ATHSEARCH_API_TOKEN_SHA256` |
| `waha` | `waha/api_key.key`, `waha/dashboard_password.key`, `waha/swagger_password.key` | `WAHA_API_KEY`, `WAHA_DASHBOARD_PASSWORD`, `WHATSAPP_SWAGGER_PASSWORD` |
| Schema Migrator backend | `schema-migrator/encrypt_key.key`, `jwt_secret.key`, `api_bearer_token.key`; `postgres.key` | `BEDROCK_ENCRYPT_KEY`, `BEDROCK_JWT_SECRET`, `BEDROCK_API_BEARER_TOKEN`, default `DATABASE_URL` password |
| Schema Migrator state store | `schema-migrator/state_db_password.key` | backend `BEDROCK_STATE_DB_PASSWORD` |
| Schema Migrator Keycloak | `schema-migrator/keycloak_database_password.key`, `keycloak_bootstrap_admin_password.key` | `KC_DB_PASSWORD`, `KC_BOOTSTRAP_ADMIN_PASSWORD` |
| Schema Migrator bootstrap Job | `schema-migrator/application_admin_password.key` | Temporary password used only when `schema-admin` is absent |

For Kubernetes, `up-ready` synchronizes these files into four Secrets:
`schema-migrator-backend`, `schema-migrator-state-db`,
`schema-migrator-keycloak`, and `schema-migrator-bootstrap`. The Keycloak realm
ConfigMap contains only realm, client, redirect, origin, and role metadata.
Credentials must never be added to that ConfigMap.

## 5. Rotation Procedures

### 5.1 Postgres password (stable bootstrap credential)

`secrets/postgres.key` is generated once and is the durable password authority. Routine
`up-ready` runs must not replace it. For Kubernetes, `up-ready` removes the file's trailing
newline before creating the Secret, marks the Secret immutable, and the Postgres pod reconciles
the persistent `sync` role to that value before its password-authenticated readiness probe can
pass. This also repairs volumes that were originally initialized with a stale password or with
the newline included in the password.

Do not edit, regenerate, or delete `secrets/postgres.key` as part of a normal stack update.
Postgres password rotation is intentionally outside the routine deployment workflow because it
requires a maintenance window and an explicit replacement of the immutable Kubernetes Secret.

### 5.2 MinIO credentials (planning required)

1. Update both secret files: regenerate `minio_access_key.key` and `minio_secret_key.key`
2. Restart minio: `docker compose up -d minio`
3. Restart minio-init: `docker compose up -d minio-init` (recreates buckets with new creds)
4. Restart consumers: `docker compose up -d java-coordinator`
5. Verify: `docker compose logs minio-init | grep "bucket_ready"` should show success

### 5.3 WireGuard obfuscation key

The obfuscation key is file-based and read at startup. To rotate without restarting the main proxy,
use the key rotator workflow in `docs/runbook.md` section 3, which spins up the `ssl-proxy-next`
candidate and migrates peers.

For a simple key rotation (accepts brief window of mismatched keys):

1. Update `secrets/wg_obfuscation_key`
2. Update `secrets/wg-rotation/candidate/secrets/wg_obfuscation_key`
3. Restart `ssl-proxy`: `docker compose restart ssl-proxy`
4. Restart `wg-udp-frontdoor`: `docker compose restart wg-udp-frontdoor`
5. Distribute new key to client `wg-obfs-shim` instances

### 5.4 Admin API key

The admin API key is file-based via `ADMIN_API_KEY_FILE`. Rotation is a simple file write and
process reload:

1. Generate new key: `openssl rand -base64 48 | tr -d '\n' > secrets/admin_api_key`
2. Copy to rotation candidate: `cp secrets/admin_api_key secrets/wg-rotation/candidate/secrets/admin_api_key`
3. Restart `ssl-proxy`: `docker compose restart ssl-proxy`
4. If `ssl-proxy-next` is running: `docker compose --profile rotation restart ssl-proxy-next`
5. Verify: `curl -H "X-API-Key: $(cat secrets/admin_api_key)" http://127.0.0.1:3002/health`

### 5.5 Atheros API token

The token is SHA-256 hashed, so clients must be updated with the raw token:

1. Generate new raw token and hash:
   ```bash
   RAW_TOKEN=$(openssl rand -base64 48 | tr -d '\n')
   echo -n "$RAW_TOKEN" | sha256sum | awk '{print $1}' > secrets/atheros_api_token_sha256.key
   ```
2. Re-render `.env`: `scripts/gen-secrets env`
3. Restart `atheros-search`:
   `docker compose --profile vector up -d atheros-search`
4. Distribute the new raw token to all API clients
5. Verify: clients with old token receive `401`; clients with new token receive `200`

### 5.6 Waha credentials

1. Regenerate the needed key file(s) in `secrets/waha/`
2. Re-render `.env`: `scripts/gen-secrets env`
3. Restart: `docker compose --profile rotator up -d waha`
4. Verify via the Waha dashboard or API health endpoint

### 5.7 Schema Migrator first-login and rotation

1. After the first successful Kubernetes deployment, read the
   `Schema Migrator first login` section of
   `secrets/up-ready-credentials.txt`.
2. Sign in as `schema-admin` and replace the temporary password immediately.
3. Store the replacement outside the repository. The Helm bootstrap Job checks
   for the user before setting any password, so later upgrades do not reset it.
4. Rotating backend encryption or authentication keys requires a planned
   restart. Rotating `encrypt_key.key` also requires a data migration strategy
   for values already encrypted with the prior key; do not replace it during a
   routine upgrade.
5. Keycloak database-password rotation must update the Postgres role and the
   `schema-migrator-keycloak` Secret together. The normal init container keeps
   them aligned on pod start, but coordinate the restart to avoid an outage.

## 6. Incident Response

### 6.1 Secret committed to git

1. **Do not** delete the commit and force-push if others may have pulled it.
2. Rotate the compromised secret immediately using the procedure in section 5.
3. Remove the file from history with `git filter-branch` or `git filter-repo` only after the
   secret is rotated and all services updated.
4. If the secret appeared in a public repo or a log aggregator, treat it as fully compromised.

### 6.2 Secret leaked via logs

1. If a secret value appeared in `docker compose logs`, identify which service logged it.
2. Rotate that secret using section 5.
3. Investigate the logging configuration: add redaction rules or fix the log statement.
4. Check external log aggregators (Loki, Promtail, etc.) for cached copies and purge them.

### 6.3 Emergency full rotation

```bash
# 1. Generate all new secrets
scripts/gen-secrets generate --force

# 2. Update .env
scripts/gen-secrets env

# 3. Recreate everything
docker compose down --remove-orphans
docker compose pull
docker compose up -d

# 4. Distribute new client keys (WireGuard PSK, obfuscation key, Atheros token)
```

## 7. Verification Commands

After any secret change, run these to confirm correct wiring:

```bash
# 1. Check no hardcoded credentials remain in compose configuration
docker compose config | grep -E 'senhamaster123|administrador' && echo "🔴 LEAK DETECTED" || echo "✅ No legacy creds"

# 2. Verify all `${VAR?}` references are resolved (will error if any are missing)
docker compose config > /dev/null 2>&1 && echo "✅ Compose config valid" || echo "🔴 Missing vars"

# 3. Check postgres auth
docker compose exec -T postgres psql -U sync -d sync -c "SELECT 1" && echo "✅ Postgres auth OK" || echo "🔴 Postgres auth failed"

# 4. Check MinIO auth
curl -s http://127.0.0.1:9000/minio/health/live > /dev/null && echo "✅ MinIO reachable" || echo "🔴 MinIO unreachable"

# 5. Check Grafana auth (requires token or cookie, but login page indicates reachable)
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3004/login

# 6. Check ssl-proxy admin API
curl -s -H "X-API-Key: $(cat secrets/admin_api_key)" http://127.0.0.1:3002/health | grep -q '"status":"ok"' && echo "✅ Admin API OK" || echo "🔴 Admin API failed"

# 7. Confirm secret file permissions and one-time-token cleanup
scripts/gen-secrets check
```

## 8. Developer Rules

**Do not:**
- Generate secrets. Run `scripts/gen-secrets generate` only on the target server.
- Copy `secrets/` to your laptop or another machine.
- Paste a secret value into Slack, a ticket, or a PR description.
- Commit `.env`, `secrets/`, any `*.key`, `*.pem`, or `*.secret` file.
- Add a secret as a default value in compose (e.g. `${MY_SECRET:-actual_value_here}`).
  Empty string defaults only.
- Log a secret value. Log *that* it was loaded.
- Pass a secret as a CLI argument (visible in `ps aux`).

**Do:**
- Use `_FILE` env vars where the service supports them (`ADMIN_API_KEY_FILE`,
  `ORACLE_PASS_FILE`, `WG_OBFUSCATION_KEY_FILE`).
- If you need a new secret, open a ticket. Do not invent your own env var and compose key
  without review.
- For local dev, run the generation script locally into a local `secrets/` that stays on your
  machine. Never use production secrets locally.
