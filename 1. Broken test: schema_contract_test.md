## Target schema

- `embeddings`: one vector table with unique `(document_id, embedding_kind, embedding_model)`.

## Backend data flow

1. Producers keep the locked topic meanings and versioned payload contracts. Every event must carry a stable event ID, schema version, occurred time, produced time, source identity, correlation ID, and causation ID.
2. Octopus validates and translates each event at the consumer boundary. Malformed records are sanitized and parked without terminating the stream.
3. Within one PostgreSQL transaction, Octopus inserts the ingestion receipt, inserts the canonical fact, updates monotonic registry state, creates any alert or search work, and records the resulting checkpoint.
4. A receipt conflict means the event was already applied. The transaction performs no counter increment or other business side effect.
5. Inventory is upserted directly from every valid observation. Device registration adds operator identity without controlling whether the device is visible.
6. Alerts identify their subject explicitly, for example `access_point/BSSID` or `station/MAC`. Severity and evidence come from backend code.
7. Octopus creates or refreshes search documents and embedding jobs. Atheros Search leases jobs, calls the embedding service, writes the vector, and completes the job in one fenced transaction.
8. Embedding outages use bounded exponential backoff with jitter. ETL health reports the open circuit, oldest job, retry count, and dependency state; recovery automatically resumes pending jobs.
9. Search health is calculated in Go with explicit queries and service-owned grants. No database view or routine contains health/business logic.
10. Schema Migrator owns all migration planning, validation, target operations, and run transitions in Scala. SQL remains parameterized backend repository code.
